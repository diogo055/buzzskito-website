# Open-source technical-SEO tools on GitHub (crawlers, link checkers, bulk Lighthouse, rendering, schema, Next.js, logs): inventory and fit for buzzskito.ca, research date 2026-10-21

## Inventory: which notable open-source technical-SEO projects exist in 2025-2026, what state are they in, and how does each fit buzzskito.ca?

### Takeaway
About 55 projects were checked. The maintained and relevant ones fall into five groups: HTML crawlers/auditors (SEOnaut, SiteOne Crawler, LibreCrawl, crawlseo, the SEOmator CLI), link checkers (linkinator, lychee, muffet), whole-site Lighthouse tools (Unlighthouse, Lighthouse CI, sitespeed.io), one maintained library that checks Google rich-result rules (Adobe structured-data-validator), and Google's own URL Inspection API. Many once-popular projects are archived or stale: Rendertron, schemarama, structured-data-testing-tool, Greenflare, seo-audits-toolkit, Yellow Lab Tools, lighthouse-batch, and the npm package of broken-link-checker.

### Cited Findings

#### How the numbers were collected (applies to every table row)
- Stars, forks, open issues, license (SPDX id), archived flag and creation date come from the public GitHub REST search API, read on 2026-10-21 ([GitHub search API docs](https://docs.github.com/en/rest/search/search)). "Last commit" is the newest commit on the default branch, from each repo's `github.com/<repo>/commits/<branch>.atom` feed. "Release" is the newest entry in `github.com/<repo>/releases.atom`. npm weekly downloads cover 2026-10-12 to 2026-10-18, from [api.npmjs.org](https://api.npmjs.org/downloads/point/last-week/linkinator). Each row links the repo the data came from.
- "STALE" means no default-branch commit in the 6 months before 2026-10-21, that is, none since 2026-04-21.
- "Ease for a non-developer" is my own assessment, based on the install steps in each README (cited in the row). It was not measured.
- Context from the brief (not web sources): about 730 static pages; build guards for sitemap, canonical and structured-data mismatches; `scripts/measure-speed.mjs` (median of 3, throttled, LCP about 3.2 s simulated); GSC and GA4 scripts; about 20 in-content links to redirected URLs; Mediavine ads installed but not yet launched; about 4,500 Amazon.ca links on 329 posts.

## Which crawler/auditor is the best free fit for a 730-page static Next.js site, and what would it find that our build guards do not?

### Takeaway
SEOnaut has the most complete maintained open-source issue list: orphan pages, page depth, redirect chains, duplicate and thin content, missing alt text, canonical-to-redirect and hreflang reciprocity. It needs Docker and MySQL, or $9 a month hosted, because the free hosted tier stops at 500 URLs. SiteOne Crawler is the easiest free option: one Windows binary, polite defaults and an HTML report. Pair either with linkinator for the redirected-link list. All three can run against a local `next build && next start`, which generates no live traffic.

### Cited Findings
- SEOnaut reports redirect chains and loops, duplicated titles and descriptions, short or long titles and descriptions, "little content", "images with no alt attribute", long alt text, missing H1, orphan pages, page depth, duplicated content, URLs blocked by robots.txt, non-indexable pages, canonical to a redirect, error or non-indexable page, canonical mismatch, multiple canonical tags, relative canonicals, 9 hreflang checks, broken external links, external links that redirect, slow TTFB, large images, images missing size attributes, excessive DOM size, missing HSTS and CSP headers, `noimageindex` and `nosnippet` ([SEOnaut translation.en.yaml](https://github.com/StJudeWasHere/seonaut/blob/main/translations/translation.en.yaml)).
- SEOnaut is Go plus MySQL and the recommended setup is Docker Compose ([README](https://github.com/StJudeWasHere/seonaut)). The hosted "Lite" plan is free for 1 project and 500 URLs per project; "Growth" is $9/month for 5 projects and 10,000 URLs per project; the self-hosted "Community" edition is free ([seonaut.org](https://seonaut.org/)). The site advertises crawling sitemaps, bypassing robots.txt and including noindex pages as options ([seonaut.org](https://seonaut.org/)).
- SiteOne Crawler ships as a single native binary for Windows, macOS and Linux. It respects robots.txt and accepts a `sitemap.xml` URL; with that it crawls only the sitemap's URLs ("sitemap-only mode"). Its defaults are `--workers=3` and `--max-reqs-per-sec=10`. The HTML report has sections for SEO, security, accessibility, performance, headers, redirects and 404s. It can test `http://localhost:3000/`, and `--ci` with `--ci-min-score` or `--ci-fail-on-code` makes it fail a build ([README](https://github.com/janreges/siteone-crawler)).
- linkinator can treat redirects as broken (`--redirects=error`) or warn about them (`--redirects=warn`), skips URLs by regex, and can scan local files ([README](https://github.com/JustinBeckwith/linkinator)).
- crawlseo's crawler stops at 2,000 pages by default and reports "16 issue types" ([README](https://github.com/crawlseo/crawlseo)). SEOmator's crawl defaults to `--max-pages 10` and `--concurrency 3` ([README](https://github.com/seo-skills/seo-audit-skill)).
- Google uses the rendered HTML to index a page, and if content is missing from the rendered HTML Google "won't be able to index it" ([Google: JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)).

### Inferences
- What a full crawl adds beyond the guards described in the brief (sitemap, canonical and structured-data consistency; Amazon, ads and photo-credit rules):
  1. internal links that point at 3xx URLs, plus redirect chains; this is the brief's "about 20 in-content links";
  2. orphan pages that sit in the sitemap with no internal links;
  3. click depth from the homepage;
  4. duplicate titles, descriptions and near-duplicate content across about 500 similar pest articles;
  5. thin pages;
  6. images with no alt or overlong alt, oversized images, and images with no width/height (a CLS risk);
  7. hreflang return-link and self-reference errors on the 7 regional pairs;
  8. canonicals that point at redirects or errors;
  9. slow TTFB per URL.
  Nothing in the brief says the guards check items 2-9.
- SEOnaut parses server HTML only (no headless-browser dependency in go.mod). That is fine for this site, because every page is statically pre-rendered. It means SEOnaut cannot see the "blank render" problem.
- Crawl the local production build, not the live site. It costs nothing on Vercel, cannot touch Mediavine, and checks the exact HTML that will be deployed. Point the crawler at the sitemap so it reaches all about 730 URLs. Then run one polite live crawl only for live-only behaviour: redirects in `next.config`, middleware and headers.
- **Exclude amazon.ca and amazon.com links from any external-link check.** SEOnaut checks external links, and linkinator and lychee will too unless told to skip them. The Amazon.ca Associates policies forbid artificially generating clicks or creating Amazon sessions, including by a robot or software program ([Amazon.ca Associates Program Policies, Participation Requirements 6(s)](https://associates.amazon.ca/help/operating/policies)). With about 4,500 Amazon links on the site (per the brief), an unfiltered link check would send thousands of automated requests through tagged links.
- Best fit for a non-developer owner: SiteOne Crawler (download, run, open the HTML report). Best fit for depth: SEOnaut, run once by Claude through Docker, or one month of the $9 hosted plan.

## Is there a maintained tool that renders pages with JavaScript like Googlebot and flags blank or broken renders?

### Takeaway
No open-source tool reproduces what Googlebot actually stored. The authoritative check is Google's URL Inspection API: it reports the indexed version only, compares Google's chosen canonical with the declared one, and its quota (2,000 per day per site) covers all 730 pages in one day. For the live render, the maintained options are: SEOmator CLI's raw-vs-rendered rules, which come closest to flagging a blank render; SiteOne Crawler's `--browser` mode, which takes a screenshot and records console errors on every page; and LibreCrawl's Playwright mode. Rendertron is archived.

### Cited Findings
- Googlebot renders with "an evergreen version of Chromium"; it queues all pages that return 200 for rendering and uses the rendered HTML for indexing. Google says to test rendering with the Rich Results Test or the URL Inspection Tool. JavaScript must not change the canonical to a different URL from the one in the original HTML ([Google: JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)).
- The URL Inspection API request takes only `inspectionUrl`, `siteUrl` and `languageCode`; the method reports on the Google index, and "you cannot test the indexability of a live URL" ([urlInspection.index.inspect](https://developers.google.com/webmaster-tools/v1/urlInspection.index/inspect)). Results include `googleCanonical` (the URL Google selected as canonical), `userCanonical` (the URL the page declares), `pageFetchState`, `lastCrawlTime`, `crawledAs`, `coverageState` and `richResultsResult` ([UrlInspectionResult](https://developers.google.com/webmaster-tools/v1/urlInspection.index/UrlInspectionResult)). That reference page also mentions a "live page" variant, which the method page contradicts; the method page is explicit that live testing is not available through the API.
- URL Inspection quota: 2,000 queries per day and 600 per minute per site; 10,000,000 per day per project ([Search Console API limits](https://developers.google.com/webmaster-tools/limits)).
- SEOmator's 16 JavaScript-rendering rules include rendered title, description, H1 and canonical present; `js-canonical-mismatch` (canonical differs between raw and rendered HTML); `js-noindex-mismatch`; `js-rendered-content` (main content present without JavaScript); `js-console-errors` (uncaught exceptions while rendering); and `js-failed-requests`. It also has `technical-empty-html` and `technical-soft-404` ([README](https://github.com/seo-skills/seo-audit-skill)).
- SiteOne `--browser` renders each page in real Chromium over the DevTools Protocol. It takes viewport or full-page screenshots, records JavaScript console errors, uncaught exceptions and failed sub-requests per page, and finds or downloads a Chrome build itself. In browser mode robots and domain-scope rules apply to the top document only, and each page is fetched twice ([README](https://github.com/janreges/siteone-crawler)).
- LibreCrawl offers "JavaScript rendering for dynamic content" through Playwright, with configurable browser engine, wait times and viewport ([README](https://github.com/PhialsBasement/LibreCrawl)).
- Rendertron (Google's headless-Chrome rendering service) is archived; its last commit was 2022-10-06 ([GoogleChrome/rendertron](https://github.com/GoogleChrome/rendertron)).

### Inferences
- In the "page keeper" problem, Google stored a blank or "Application error" render and then folded the page into another site's canonical. The direct detector is `googleCanonical` differing from `userCanonical`, or `googleCanonical` pointing off-domain, from the URL Inspection API. That can be run weekly over all new guides within quota through the GSC MCP server already in the workspace. No crawler can see Google's stored render.
- Live-render tools catch only failures that reproduce today: deterministic hydration crashes, missing canonical after hydration, console exceptions, failed chunk requests. A transient failure that hit Googlebot once will usually not reproduce. So run SEOmator's `js-*` rules or SiteOne `--browser` on the local build after each release, as a regression check, and use the URL Inspection API for "what did Google keep".
- Googlebot renders with evergreen Chromium, so any current headless Chromium (Playwright, Puppeteer or CDP, as these tools use) approximates its renderer. None of these tools emulates Googlebot's render queue, timeouts or resource limits.

### Gaps
- Not researched: whether any tool compares a page's rendered output against the copy Google stored; whether the blank renders come from deploy-time JavaScript chunk mismatches.
- SEOmator's thresholds for `js-rendered-content` and `technical-empty-html` are not documented in the README excerpt read.

## Which bulk Lighthouse/CWV tool is best, and does it beat our own script?

### Takeaway
Unlighthouse is the best open-source tool for running Lighthouse across all about 730 pages. It runs the same Lighthouse engine, so it does not measure more accurately than `scripts/measure-speed.mjs`; it adds whole-site coverage, grouping and a UI. Its defaults must be changed: `maxRoutes` is 200, `samples` is 1, and throttling is off for localhost. Lighthouse CI fits per-deploy regression gates on a few template URLs. sitespeed.io is a heavy monitoring stack. Real Core Web Vitals (what users experience) come from field data: the CrUX API (free, 150 queries a minute, API key required) or the web-vitals library, not from any lab tool.

### Cited Findings
- Unlighthouse defaults: samples 1; throttle true, but localhost and 127.0.0.1 run unthrottled unless set explicitly; dynamicSampling 8; maxRoutes 200; sitemap, crawler and robotsTxt true; device mobile; cache true; `ci.budget` takes a score or per-category scores; concurrency defaults to the available CPU cores ([Unlighthouse config](https://unlighthouse.dev/api-doc/config)). `lighthouseOptions` are passed directly to Lighthouse, for example `throttlingMethod: 'devtools'` and `onlyCategories: ['performance']` ([Unlighthouse Lighthouse guide](https://unlighthouse.dev/guide/guides/lighthouse)). It requires Node 22.18 or later ([README](https://github.com/harlan-zw/unlighthouse)).
- Lighthouse CI collects 3 runs per URL by default (`--numberOfRuns`), can start a server (`startServerCommand`) or serve a static directory (`staticDistDir`), and has an upload target named `temporary-public-storage` ([LHCI configuration](https://github.com/GoogleChrome/lighthouse-ci/blob/main/docs/configuration.md)). Its last release is v0.15.1 from 2025-06-26, although commits continued to 2026-10-19 ([repo](https://github.com/GoogleChrome/lighthouse-ci)).
- sitespeed.io drives real browsers and adds video and visual metrics, a HAR waterfall and "Coach" advice. Monitoring sends metrics to Graphite or InfluxDB for Grafana ([README](https://github.com/sitespeedio/sitespeed.io)).
- lighthouse-parade crawls a domain, runs Lighthouse on each page and writes one aggregated CSV with a Google Sheet template; its concurrency defaults to CPU cores minus one ([README](https://github.com/cloudfour/lighthouse-parade)).
- CrUX API: page-level and origin-level data, including LCP, INP and CLS; 150 queries per minute per Google Cloud project; free, with no way to buy more quota; needs an API key for the Chrome UX Report API ([CrUX API docs](https://developer.chrome.com/docs/crux/api)).
- Lighthouse flags available for site-wide runs include `--blocked-url-patterns`, `--throttling-method` (devtools, provided, simulate) and `--only-categories` ([Lighthouse readme](https://github.com/GoogleChrome/lighthouse/blob/main/readme.md)).

### Inferences
- Unlighthouse does not "beat" the existing script on accuracy: both are Lighthouse lab runs. It beats it on coverage. One scan of all pages, with maxRoutes of 750 or more and samples of 3 to match the median-of-3 method, would show which templates or pages are outliers. The single 3.2 s baseline cannot show that.
- Risk specific to this machine: the brief says plain headless Lighthouse here reported a false LCP of about 9 s unless four Chrome flags are passed. Unlighthouse launches its own Chrome through Puppeteer, so calibrate it on 3 URLs against `scripts/measure-speed.mjs` before trusting a full scan. Passing the same flags through its Puppeteer options is likely needed (not verified).
- On localhost, Unlighthouse is unthrottled by default. Comparisons with the 3.2 s simulated baseline need throttling turned on explicitly.
- For ranking-relevant numbers, lab tools are a proxy. Per-URL field data exists only where CrUX has enough traffic, which is probably limited to the top pages of this site. The web-vitals library feeding GA4 would be the only way to get per-page field data the assistant can read, since Vercel Speed Insights is owner-only per the brief.
- Verdicts: Unlighthouse, adopt now as a one-off, then maybe quarterly. Lighthouse CI, maybe later, with 5-10 template URLs as a GitHub Actions gate. sitespeed.io, skip. lighthouse-parade, maybe later only if a CSV is preferred. web-vitals to GA4, maybe later. CrUX API, maybe later.

### Gaps
- The CrUX API page read does not say what the API returns for a URL without enough traffic.
- It was not confirmed that Unlighthouse accepts `blockedUrlPatterns` inside `lighthouseOptions`. It says it passes options "directly", and Lighthouse supports the flag, but this was not tested.
- No independent benchmark comparing Unlighthouse numbers with single Lighthouse or PageSpeed Insights runs was found.

## Which schema/structured-data validators check against Google's actual rich-result requirements?

### Takeaway
Only Google's own surfaces are authoritative: the Rich Results Test (manual), Search Console enhancement reports, and the URL Inspection API's `richResultsResult` (indexed version). The one maintained open-source library that encodes Google rich-result rules is Adobe's `structured-data-validator`. It is Apache-2.0, has 8.7K npm downloads a week but only 17 stars, and has no handlers for Article, FAQPage or LocalBusiness. The Schema Markup Validator and schema-dts check the schema.org vocabulary, not Google eligibility. schemarama is archived and structured-data-testing-tool is abandoned. Google retired FAQ rich results on 2026-05-07 and stopped showing HowTo rich results in September 2023, so validators' FAQ and HowTo checks no longer predict any rich result.

### Cited Findings
- Adobe's library "validates structured data against both Schema.org and Google Rich Results specifications". It returns ERROR or WARNING issues such as a missing required `price`, and takes input from `@marbec/web-auto-extractor` ([README](https://github.com/adobe/structured-data-validator)). The Google-specific type handlers present are Product, Offer, AggregateOffer, MerchantReturnPolicy, OfferShippingDetails, ShippingDeliveryTime, BreadcrumbList, ListItem, ImageObject, JobPosting, Organization, Person, Recipe, Review, Rating, AggregateRating, VideoObject, Clip, BroadcastEvent, SeekToAction, HowToStep/Section/Direction/Tip, 3DModel, Certification, among others ([src/types](https://github.com/adobe/structured-data-validator/tree/main/src/types)). Stats: 17 stars, v1.7.0 on 2026-02-25, 8,731 npm downloads in the week of 2026-10-12 ([npm API](https://api.npmjs.org/downloads/point/last-week/@adobe/structured-data-validator)).
- FAQ rich results: Google's FAQPage documentation records "Deprecating the FAQ rich result feature" (2026-05-08: the feature "will no longer appear in Google Search starting May 7, 2026") and "Removing documentation for the FAQ rich result feature" (2026-06-15: no longer shown in Google Search results). A September 2023 entry removed the How-to documentation because that rich result is no longer shown ([Google FAQPage docs changelog](https://developers.google.com/search/docs/appearance/structured-data/faqpage)).
- URL Inspection API: `richResultsResult` is "Result of the Rich Results analysis", absent when no rich results are found, with detected items and per-item issues ([UrlInspectionResult](https://developers.google.com/webmaster-tools/v1/urlInspection.index/UrlInspectionResult)). Quota: 2,000 per day per site ([limits](https://developers.google.com/webmaster-tools/limits)).
- Schema.org's Schema Markup Validator (validator.schema.org, launched 2021 as the successor to Google's Structured Data Testing Tool) checks markup against the full schema.org vocabulary, whether or not Google supports it. Google points people to the Rich Results Test for Google-specific checks ([schema.org blog](https://blog.schema.org/2021/05/21/announcing-schema-markup-validator-validator-schema-org-beta/); [Search Engine Land](https://searchengineland.com/?p=348590)).
- SEOmator's structured-data rules include `schema-required-fields`, `schema-article`, `schema-breadcrumb`, `schema-faq` and `schema-local-business` ([README](https://github.com/seo-skills/seo-audit-skill)).
- schema-dts provides TypeScript types for the schema.org vocabulary ([google/schema-dts](https://github.com/google/schema-dts)). schemarama is archived (2022) ([google/schemarama](https://github.com/google/schemarama)). structured-data-testing-tool's last commit is 2022-05-04 and its last npm release is 2020-03-11 ([repo](https://github.com/iaincollins/structured-data-testing-tool); [npm](https://registry.npmjs.org/structured-data-testing-tool)).

### Inferences
- For this site the relevant Google rich-result types are BreadcrumbList, image metadata (ImageObject), Organization and logo, and reviews or ratings where allowed. Adobe's library has handlers for exactly these, so it could become a build guard next to `check:sitemap`. Its lack of Article, FAQPage and LocalBusiness handlers matters less, because FAQ rich results are retired.
- The brief says FAQ, HowTo and Speakable markup is on every page. Google retired FAQ and HowTo rich results, so no validator "pass" on those types will produce a rich result. The researched sources do not say the markup is harmful, and whether to keep it is a separate decision.
- The GSC "Improve item appearance" image-metadata warnings are the one schema issue live on the site. Adobe's `ImageObject` handler may cover them, but which fields it checks was not read. The most reliable loop is to fix the markup, then confirm through the URL Inspection API's `richResultsResult` or the Search Console report.
- Verdicts: Adobe validator, maybe later (worth a spike as a build guard). schema-dts, maybe later. Schema Markup Validator, use ad hoc only. schemarama, structured-data-testing-tool and extruct, skip. SEOmator schema rules: run them only as part of a SEOmator trial, and treat its FAQ rule as outdated.

### Gaps
- Which ImageObject fields Adobe's handler requires or warns about (versus Google's image-metadata documentation) was not read.
- Whether Adobe's rule set has been updated for Google's 2026 FAQ retirement is unknown. The main branch's last commit is 2026-02-25, before the retirement.
- The exact fields GSC flags under "Improve item appearance" for this site were not researched.

## Security and safety: which tools are mature and widely used vs single-maintainer projects, and what are the risks of running them against the live site (rate limits, Vercel costs, Mediavine invalid traffic)?

### Takeaway
The mature, widely used tools are backed by organizations: Lighthouse, Lighthouse CI, web-vitals and schema-dts (Google), axe-core (Deque), Crawlee (Apify), lychee (lycheeverse). Most of the useful crawlers are personal projects or very new: SEOnaut, SiteOne, LibreCrawl (Sept 2025), crawlseo (Apr 2026) and SEOmator CLI (Jan 2026). Vercel cost from one polite crawl of about 730 pages is negligible. The real risks are, first, any tool that executes JavaScript on live ad pages (Lighthouse, Unlighthouse, browser-mode crawlers), because it would create automated ad impressions; and second, link checkers that request the about 4,500 tagged Amazon links. Run rendering tools against the local build or before ads launch, block ad URLs, and exclude Amazon from link checks.

### Cited Findings
- Politeness defaults: SiteOne uses 3 workers and 10 requests/s and warns that high settings "can cause a DoS attack" ([README](https://github.com/janreges/siteone-crawler)). linkinator defaults to 100 simultaneous connections ([README](https://github.com/JustinBeckwith/linkinator)). In its own comparison table, lychee is the only checker marked as respecting rate limits, and it has per-host concurrency and per-host request-interval options ([README](https://github.com/lycheeverse/lychee)). crawlseo follows robots.txt per RFC 9309 and honours Crawl-delay ([README](https://github.com/crawlseo/crawlseo)). SEOmator's default concurrency is 3 ([README](https://github.com/seo-skills/seo-audit-skill)). Unlighthouse's concurrency defaults to the available CPU cores ([config](https://unlighthouse.dev/api-doc/config)). lighthouse-parade defaults to CPU cores minus one ([README](https://github.com/cloudfour/lighthouse-parade)). LibreCrawl has configurable delays and a robots.txt setting ([README](https://github.com/PhialsBasement/LibreCrawl)).
- Lighthouse's default mobile emulated user agent is an ordinary Chrome string: `Mozilla/5.0 (Linux; Android 11; moto g power (2022)) ... Chrome/136.0.0.0 Mobile Safari/537.36`, with no Lighthouse or bot token ([core/config/constants.js](https://github.com/GoogleChrome/lighthouse/blob/main/core/config/constants.js)).
- Google Ad Manager defines invalid traffic as clicks or impressions that may artificially inflate an advertiser's costs or a publisher's earnings; publishers clicking their own ads and automated clicking tools are examples ([Ad Manager help: Invalid traffic](https://support.google.com/admanager/answer/12331294)). Google's "known crawler" category of general invalid traffic covers automated programs that "declare" themselves as non-human, usually listed in the IAB International Spiders and Bots List ([Campaign Manager 360 help: GIVT impressions](https://support.google.com/campaignmanager/answer/7443744)).
- Amazon.ca Associates: Participation Requirement 6(s) bars artificially generating clicks or impressions or creating Sessions on an Amazon Site, including by a robot or software program. Commission rules disqualify Bounty and Bonus events that involve "use of bots or automated software" ([Amazon.ca Associates Program Policies](https://associates.amazon.ca/help/operating/policies)).
- Vercel: Hobby is "restricted to non-commercial personal use only", and ads or affiliate-led sites count as commercial. Hobby includes 100 GB Fast Data Transfer, 1,000,000 function invocations, 5K image-optimization transformations, 300K image cache reads and 100K cache writes a month. On Pro, Fast Data Transfer is "Flat Rate CDN" and other resources bill on demand after the monthly credit, for example $0.60 per 1M invocations and $0.05 per 1K image transformations ([Vercel fair use guidelines](https://vercel.com/docs/limits/fair-use-guidelines)). Edge middleware may use no more than 50 ms of CPU on average ([same page](https://vercel.com/docs/limits/fair-use-guidelines)).
- Vercel runtime logs are kept 1 hour on Hobby, 1 day on Pro and 3 days on Enterprise ([Vercel limits](https://vercel.com/docs/limits)). Drains, which can forward "runtime, build, and static logs", are Pro and Enterprise only and are billed by volume at $0.50 ([Vercel Drains](https://vercel.com/docs/drains)). The Search Console Crawl Stats report shows Googlebot requests by response, file type, purpose (discovery or refresh) and Googlebot type, plus host status, for root-level properties only ([Search Console Help: Crawl Stats](https://support.google.com/webmasters/answer/9679690)).
- Data leaving the machine: SiteOne uploads the HTML report to `crawler.siteone.io` only with `--upload` (default retention 30 days) ([README](https://github.com/janreges/siteone-crawler)). crawlseo lists every outbound host it contacts, including a daily GitHub release check that can be disabled ([README](https://github.com/crawlseo/crawlseo)). LibreCrawl's standard mode has multi-user registration; the README recommends Local Mode bound to 127.0.0.1 for personal use ([README](https://github.com/PhialsBasement/LibreCrawl)).
- Licenses to watch: seo-ops and seo-audits-toolkit carry no license; python-seo-analyzer, site-audit-seo and WebPageTest show NOASSERTION; Greenflare and image-actions are GPL-3.0; LinkChecker and Yellow Lab Tools are GPL-2.0; pa11y is LGPL-3.0 (repo data, [GitHub search API](https://docs.github.com/en/rest/search/search)). ### Inferences
- **Mediavine and invalid traffic.** HTML-only crawlers do not execute JavaScript: SEOnaut, SiteOne in default mode, linkinator, lychee, muffet, crawlseo, advertools. They therefore never run the Mediavine script or request ads. Tools that execute JavaScript do: Lighthouse, Unlighthouse, Lighthouse CI, lighthouse-parade, sitespeed.io, SiteOne `--browser`, LibreCrawl JS mode, SEOmator's renders, crawlseo and LibreCrawl's PageSpeed calls. On a live ad page these would load ads. Lighthouse's default user agent looks like a normal phone, so those impressions would not be filtered as a "declared" known crawler. That is exactly the automated, artificially inflating traffic Google's IVT definition describes. Safe order of preference:
  1. run JS tools against the local production build with ads off (`ADS_ENABLED` kill switch, per the brief);
  2. run them on the live site before Mediavine launches; the brief says ads are installed but not live;
  3. after launch, block the ad network URL patterns with Lighthouse `--blocked-url-patterns` (Unlighthouse passes `lighthouseOptions` through) and keep runs small.
- Mediavine itself did not come up in searches about testing tools. Its exact policy is a gap. Treat Google's IVT rules as the floor, because Mediavine sells through Google's ad stack (an assumption; not verified here).
- **Amazon.** Any link checker that follows external links would request tagged amazon.ca and amazon.com URLs, which risks breaching rule 6(s) and polluting click reports. Always pass a skip pattern for `amazon\.` (linkinator `--skip`, lychee exclude options) and disable SEOnaut's external-link checking or accept the risk knowingly.
- **Vercel cost.** One crawl of about 730 HTML pages plus their assets is tiny next to Hobby's 100 GB or Pro's flat-rate CDN. Static pages served from cache should not invoke functions, but the site's `middleware.ts` (per the brief) runs on page requests, and a crawl adds about 730 middleware invocations, about $0.0004 at $0.60 per 1M. The one cost that could move is Next.js image optimization: a crawler or Lighthouse run that downloads every `/_next/image` variant could create uncached transformations. Even 10,000 of them would cost about $0.50 on Pro, but they would use up the 5K/month Hobby allotment. Prefer the local build for image-heavy crawls.
- **Logs.** On Vercel, raw access-log analysis (GoAccess, advertools) needs paid Drains (Pro), and the runtime-log window is only 1 hour or 1 day. For this site, GSC Crawl Stats plus the URL Inspection API answer most "what is Googlebot doing" questions for free. Log tooling is maybe-later at best.
- **Single-maintainer risk.** The recommended one-off tools (SEOnaut, SiteOne, Unlighthouse, linkinator) are personal projects, but they run locally, need no accounts and are used only occasionally. If one goes unmaintained, nothing breaks in production. Only tools wired into the build (an Adobe validator guard, Lighthouse CI) create a maintenance dependency, and those are the organization-backed ones.
- The site's middleware returns 403 to Singapore and China unless the user agent declares a crawler (per the brief). Crawls from the owner's machine in Canada are unaffected, but a cloud-hosted crawler in those regions would be blocked.
